# Day 7：Embedding 与检索策略消融实验计划

## 目标

回答两个具体问题：

1. 更强、更大的 Embedding 模型是否在我们的中英文技术文档上带来可测量的召回提升？
2. 提升来自 Embedding 模型本身、词级 BM25、字符 n-gram BM25、查询翻译，还是 RRF 混合检索？

## 前置条件

- Day 4：词级与字符 n-gram BM25 检索实现完成。
- Day 5：RRF 融合和去重实现完成。
- Day 6：准备 30～50 条人工核验问题，每条标注至少一个相关 chunk/document id。
- 评测程序能够输出 Recall@1、Recall@3、Recall@5 和 MRR。

前置条件未满足时不提前宣布某个模型更好。

## 实验组

| 组别 | Embedding | 词级 BM25 | 字符 BM25 | 查询翻译 | 家族/全局融合 | 目的 |
|---|---|---:|---:|---:|---:|---|
| A | MiniLM Baseline | 否 | 否 | 否 | 否 | 当前轻量稠密检索基线 |
| B | Qwen3-Embedding-0.6B | 否 | 否 | 否 | 否 | 只观察更换 Embedding 的影响 |
| C | 无 | 是 | 否 | 否 | 否 | 观察词级精确匹配能力 |
| D | 无 | 否 | 是 | 否 | 否 | 观察词典外专业词召回能力 |
| E | 无 | 是 | 是 | 是 | BM25 家族 | 观察翻译增强的跨语言词法召回 |
| F | MiniLM Baseline | 是 | 是 | 是 | 家族 + RRF | 观察轻量 Dense 与 BM25 家族融合收益 |
| G | Qwen3-Embedding-0.6B | 是 | 是 | 是 | 家族 + RRF | 观察更强 Dense 与融合后的最终收益 |

如果时间和机器资源允许，再把 `multilingual-e5-large-instruct` 作为可选 H 组；它不是完成 Day 7 的必要条件。

## 必须固定的变量

- 使用完全相同的原始文档和解析结果；
- 使用完全相同的 Chunk 文本、ID、大小和 overlap；
- 使用完全相同的评测问题和人工相关性标注；
- 使用完全相同的 top-k；
- 使用同一份评测代码；
- 记录模型名称、版本、向量维度和查询 instruction；
- 测延迟前先完成一次预热，并分别记录索引时间和查询时间。

若更换模型时重新切块，就不能把结果差异只归因于 Embedding 模型。

## 指标

### 质量

- Recall@1、Recall@3、Recall@5；
- MRR；
- 中译英和英译中交叉检索子集各自的 Recall@3；
- 专有名词、缩写和精确字符串子集的 Recall@3；
- 失败问题清单和失败原因分类。

### 工程代价

- 模型下载/磁盘大小；
- 向量维度和索引占用；
- 首次建索引时间；
- 预热后的平均查询延迟、P50 和 P95；
- 峰值内存；
- CPU/GPU 运行条件。

### 翻译器子实验

在相同跨语言问题子集上固定 BM25、Chunk 和 top-k，比较：

1. 不翻译；
2. 本地 `Qwen/Qwen3-0.6B` 双向翻译；
3. 本地 `Helsinki-NLP/opus-mt-zh-en` 单向基线；
4. DeepSeek 双向查询翻译。

记录两个方向各自的跨语言 Recall@1/3/5、术语翻译失败案例、模型加载时间、预热后翻译延迟和外部 API 依赖。不能因为模型“离线”或参数更多就预设它一定更好。

余弦分数不是跨模型可直接比较的置信度，因此不比较“哪个模型平均 score 更高”，只比较排名指标和资源指标。

## 预先约定的选型规则

1. 质量首先看 Recall@3，其次看 MRR 和失败案例。
2. 暂定只有 Recall@3 提升至少 3 个百分点，或明确解决关键中英文查询失败时，才认为大模型带来有意义收益。
3. 若质量提升不足 3 个百分点且查询延迟或内存显著增加，默认保留 MiniLM。
4. 若两路 BM25 + RRF 已解决大部分专有名词问题，不为了模型参数量盲目升级。
5. 最终结论必须同时报告收益和代价，不能只展示最好的一列。

3 个百分点是项目的预注册工程阈值，不是行业通用标准；看到结果后不得为了制造正面结论再修改阈值。
